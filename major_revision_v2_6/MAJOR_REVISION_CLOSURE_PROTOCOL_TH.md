# ConveyorFlow v2.6 — protocol เพื่อปิดข้อกังวล Major Revision

สถานะ: **design draft; ยังไม่ freeze cohort หรือเริ่ม paid v2.6 calls**. ผล v2.3–v2.5 เป็นหลักฐานก่อนหน้า ไม่เปลี่ยนย้อนหลังและไม่ pool กับ v2.6 โดยอัตโนมัติ. การปิดข้อกังวลหมายถึงมีหลักฐานตรงกับ **ข้ออ้างที่จำกัดขอบเขตไว้ล่วงหน้า** ไม่ได้หมายถึงบังคับให้ CF-Fit ชนะทุก metric หรือรับประกันผลตีพิมพ์.

## 1. คำถามและข้ออ้างที่จะทดสอบ

**RQ1:** เมื่อ task ที่ dependency พร้อมไหลบน shared READY belt การเลือกงานด้วยตนเองของ agents ส่งผลต่อ verified throughput, restricted task-completion time, busy/productive utilization และ token/provider cost อย่างไรเมื่อเทียบกับ (ก) Central-Rule-Matched ซึ่งใช้ fit/stand-down, team, belt, CAS, verifier และ horizon เดียวกัน แต่ให้ process ส่วนกลางตัดสินใจ กับ (ข) Static-Owners ซึ่งกำหนดเจ้าของก่อนรัน? รายงานผลเป็น vector/trade-off ไม่รวมเป็นคะแนนเดียวและไม่ตั้งสมมติฐานว่าต้องชนะทุกด้าน.

**RQ2:** ความต่างของ Ability Rank ที่วัดจากงาน calibration แยกจาก main ช่วย CF-Fit ภายใต้ heterogeneous team เทียบ homogeneous team อย่างไร? ใช้ simulation/ablation ที่มีอยู่เป็นหลัก; ถ้าเพิ่ม real-LLM composition ให้เป็นชุดทดลองแยก ไม่แทรกเข้า RQ1 โดยไม่ตรึงแผน.

Scientific contribution ที่ทดสอบคือ *decentralized self-selection + capability heterogeneity + fit/stand-down*. จำนวน policies เป็นตัวควบคุมและ ablation ไม่ใช่ contribution. Atomic claim และ verifier เป็น shared infrastructure; จึงห้ามเรียกทั้งระบบว่าไม่มี single point of failure.

## 2. สองการทดลองที่ตอบ reviewer คนละข้อ

**E1 — implementation-level matched decision-locus test (ไม่เรียก LLM):** นำ DAG/job arrivals, ability vectors, fit scores, stand-down rule, service outcomes, tie seed และ observation window **ชุดเดียวกัน** ป้อนให้ agent-local CF-Fit และ Central-Rule-Matched. ตรวจ no-fault proposal/claim parity, PID ของผู้ตัดสินใจ, CAS uniqueness, decision latency และ terminal states. Inject outage เฉพาะ coordinator แล้ว inject shared belt/claim-store outage เป็น negative control. ความต่างใน E1 ตีความได้ที่ *allocation-decision process dependency* เท่านั้น ไม่ใช่ production reliability. ต้องใช้ workload traces ใหม่ตาม E2 และมี audit แยก; v2.4 fault test เป็น pilot ที่เปิดเผยแล้ว ไม่แทนการทดสอบใหม่บน source ที่ขยาย.

**E2 — live MFEC Real-LLM paired allocation:** แต่ละ source-paired block มี full ML Build DAG 1 งาน (ingest→preprocess→train→package) และ repository repair 1 งานบน READY belt เดียวกัน. รัน 3 arms โดยสุ่ม/ถ่วงดุล arm order จาก hash ที่ตรึง, prompts/model versions/ability profile/verifier/horizon เท่ากัน, one attempt ต่อ agent–task และไม่มีการส่งซ้ำอัตโนมัติหลัง provider timeout. E2 วัด *ผลการดำเนินงานรวมภายใต้ระบบจริง*; latency ของ gateway, model stochasticity และ agent assignment เป็นส่วนหนึ่งของผล ไม่อ้างว่าแยก causal effect ของ decision locus อย่างบริสุทธิ์. E1 เป็นหลักฐานแยกกลไก, E2 เป็น ecological validation.

## 3. Source frame และขนาดตัวอย่างก่อนเห็นผลใหม่

- Unit สำหรับ inferential/descriptive uncertainty คือ **repository project**; bugs, stages, repeated seeds และ API calls ใน project เดียวกันเป็น nested observations. ML corpus เป็นอีก cluster หนึ่งที่ต้องแสดงการวิเคราะห์แยกหรือ leave-one-corpus-out.
- Frame เริ่มจาก 17 BugsInPy projects ใน manifest ที่ snapshot/hash ไว้. คัด projects ด้วย hash order ที่ตรึงก่อน outcome; ภายใน project ทดสอบ candidate bugs ตาม hash order; เก็บ preflight exclusions ทั้งหมด. เลือก **2 bugs แรกที่ผ่าน** buggy-fail/fixed-pass, gold-free, public-regression และ image/provenance audit ต่อ project. ไม่เลือกจากคำตอบ LLM. Project ที่ได้ <2 qualified cases ถูกตัดตาม gate และแสดงใน flow diagram. `youtube-dl` คือ source repository Python เพิ่ม ไม่ใช่การดาวน์โหลดวิดีโอในงานทดลอง; bug 27 ที่ผ่าน preflight v2.5 นับเป็น prior exposure และต้องกำหนดการใช้/การไม่ใช้ก่อน freeze cohort.
- สร้าง **prior-attempt exclusion ledger** จาก provider request markers ของ v2.3–v2.5 ทุกชุดก่อนคัด case. Case ที่เคยเรียก LLM จะไม่เข้า v2.6 main แม้เคยล้มเหลว; การตัดต้องดู marker ไม่ดูผลสำเร็จ. `youtube-dl` bug 27 ยังไม่เคยเรียก LLM จึงเป็น candidate ได้ แต่ต้องเปิดเผย pre-provider selection ที่เกิดก่อน v2.6; sensitivity ตัด case ที่เคย preflight ก่อน protocol นี้. ไม่เรียก previous exposure ว่า independent held-out test.
- เป้าหมาย prospective cohort คือ **12 distinct repository projects × 2 cases = 24 paired blocks**. หาก frame 17 projects ให้ได้ไม่ถึง 12 qualified projects ให้หยุดที่ eligibility outcome และจำกัดผล E2 เป็น multi-source feasibility; ห้ามเติม projects หรือผ่อนเกณฑ์หลังเห็น LLM outcomes. รอบ v2.4/v2.5 แสดงแยกเป็น preceding exploratory cohorts ไม่ใช้เพิ่ม N ของ v2.6.
- ML pool เป้าหมาย **6 public corpora** ขนาด ≥20,000 records: Adult, Beijing, Bank Marketing, Covertype ที่มี provenance เดิม และ candidate ใหม่ [UCI Letter Recognition](https://archive.ics.uci.edu/dataset/59/letter) (20,000) กับ [UCI Statlog Shuttle](https://archive.ics.uci.edu/dataset/148/statlog+shuttle) (58,000). ก่อน main ต้อง download/hash, ตรวจ license, split, leakage, baseline quality, frozen hidden verifier และรัน trusted full-DAG smoke ใน short-path Podman สำหรับ corpus ใหม่. Pair corpora แบบ balanced (4 blocks/corpus) ด้วย deterministic assignment; 2 cases ของ project เดียวต้องใช้คนละ corpus.
- ทีม ≤3 models จาก MFEC รุ่นที่ exact version ตรึงไว้. Ability Rank 1/2/3 เป็น **empirical verified capability บน calibration tasks ที่ไม่อยู่ใน main** ไม่ใช่อายุรุ่น/ราคาหรือการเรียก Strong–Mid–Weak. ราคา/token เป็น resource dimension แยก. ถ้ารุ่นโมเดลหรือ calibration เปลี่ยนระหว่าง cohort ต้องหยุดและออก amendment ไม่ rewrite lock.
- ก่อน freeze main ให้เผยแพร่ `ability_profile` พร้อมจำนวนงาน calibration, verified/failed/unresolved ต่อ model × task family, วิธีจัดอันดับ deterministic และ uncertainty. ใช้ calibration ที่ case ไม่ซ้ำกับ main; เรียง rank จาก verified rate ที่ปรับ smoothing ล่วงหน้าและให้ **rank เท่ากัน** เมื่อข้อมูลไม่แยกความสามารถอย่างน่าเชื่อถือ แทนการบังคับให้มี 1/2/3 ทุก task. ต้องระบุว่า rank ของ repository ใหม่เป็นการ transport จาก calibration ไม่ใช่ผลทดสอบของ case นั้นเอง. Difficulty ของ ML stages/repair ให้กำหนดจาก rubric ที่เห็นได้ก่อนรู้ gold/LLM outcome; verifier ไม่ใช้คำตัดสินของ agent เป็นเฉลย.
- สูงสุดตาม task DAG = 5 provider attempts/arm/block; 24 blocks × 3 arms × 5 = **360 main attempts** (เพดานป้องกัน runaway ไม่ใช่จำนวนที่จะยิงให้ครบ). Calibration และ gateway probes แยก ledger และไม่นับเป็น main. จำนวนจริงลดลงเมื่อ upstream fail; รันครบทุก eligible block ไม่หยุดเมื่อทิศทางผลถูกใจ.

ความเสี่ยงด้าน feasibility: manifest มี 17 projects แต่บาง project ประกาศ Python 3.6/3.7 และอาจสร้าง environment/test ไม่สำเร็จ. ต้องรายงานจำนวนที่ qualify จริง ไม่ถือว่า 17 projects พร้อมรัน. งาน repository สาธารณะยังอาจอยู่ในข้อมูลฝึกของโมเดล; การแยก gold patch ออกจาก prompt และ image ป้องกัน **evaluation-time leakage** แต่ไม่พิสูจน์ว่าไม่มี **pretraining contamination**. จึงห้ามอ้างความสามารถบน unseen repositories โดยไม่มีหลักฐานเพิ่มเติม. ไม่ใช้ SWE-bench Verified มาเติม N อัตโนมัติ เพราะมี [คำเตือนเรื่อง contamination จากผู้จัดทำเอง](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/); benchmark อื่นต้องผ่าน protocol ใหม่.

## 4. Estimands และการวิเคราะห์ที่ตรึงก่อน paid calls

Primary contrast: paired project-level mean difference `CF_FIT − CENTRAL_RULE_MATCHED` ของ **verified jobs per fixed 3,600 s block** (หรือ jobs/hour เมื่อ horizon = 1 h). Secondary control contrast: `CF_FIT − STATIC_OWNERS`. ภายใน project เฉลี่ยสอง case-block ก่อนคำนวณ uncertainty ระหว่าง projects; รายงานแต่ละ project และ pooled point estimate พร้อม 95% interval ที่ใช้ project เป็นหน่วย โดยระบุว่าการเลือก BugsInPy projects ไม่ใช่ probability sample ของ repositories ทั้งโลก. อย่ารายงาน provider attempts 360 เป็น N.

Time: นิยาม `T*_j = min(time from arrival to verified completion, H − arrival)` โดยงานที่ไม่ verified ก่อน horizon ได้ค่า `H − arrival`. รายงาน mean restricted time ของ **ทุก arrived job** จึงไม่เปรียบเทียบเฉพาะ subset งานที่สำเร็จต่างกัน; conditional completion time ของ verified jobs เป็น secondary เท่านั้น. รายงาน success/abandonment และ dead-letter คู่กันเสมอ.

Utilization: busy fraction = executor-occupied time / available agent-time; productive fraction = execution time ของ verified tasks / available agent-time. Busy สูงไม่ได้แปลว่าดี. Token counts เป็น measured resource; billed cost/job คำนวณเฉพาะเมื่อทุก provider attempt มี currency, billed amount และ request identity ที่ reconcile กับ MFEC export. ถ้าขาดแม้หนึ่ง attempt ให้ cost/job ของ scope นั้นเป็น `null`; รายงาน missingness กับ provider-reported units แยก และ **ตัด real-LLM monetary efficiency claim**. Simulation cost เป็น assumption/sensitivity ไม่ใช่ใบแจ้งหนี้.

ไม่ใช้ p-value หรือ CI ข้ามศูนย์เป็นเกณฑ์ “งานผ่าน”; รายงาน effect, interval, source-level heterogeneity, source exclusion flow และ sensitivity (leave-one-project-out, leave-one-corpus-out, ตัด block ที่เคย exposed ถ้ามี). **ไม่กล่าวว่าเทียบเท่า/non-inferior** เว้นแต่ margin และ sample-size justification ถูกอนุมัติ/ตรึงก่อน paid calls และ CI อยู่ภายในเกณฑ์นั้น. ค่า SD จาก 4 projects ใน v2.4 ไม่น่าเชื่อถือพอเป็น power estimate เดียว; เป้าหมาย 12 projects ช่วยเพิ่มความหลากหลายแต่ไม่รับประกัน CI แคบ. แนวคิดกำหนด N จาก precision/SESOI อิง [Lakens, 2022](https://doi.org/10.1525/collabra.33267); การรายงานจำนวน clusters และข้อจำกัดของการอนุมานอิงหลักการของ [CONSORT cluster extension](https://www.bmj.com/content/345/bmj.e5661) **เป็นแนวทางรายงานเท่านั้น—งานนี้ไม่ใช่ clinical cluster trial**.

ตัวอย่างความเสี่ยงด้าน precision จากสูตร `t(0.975, n−1) × SD / √n`: ที่ 12 projects ถ้า between-project SD จริงเป็น 0.5 jobs/hour ช่วง 95% มี half-width ประมาณ 0.318; ถ้า SD = 1.0 จะกว้างประมาณ 0.635 jobs/hour. นี่เป็น **scenario ไม่ใช่ผลจริงหรือ power guarantee**. ดังนั้นถ้าที่ปรึกษาต้องการความละเอียด ±0.25 jobs/hour หรือพิสูจน์ equivalence จริง **target 12 projects ไม่พอรับประกัน**; ต้องขยาย source frame/กำหนด N ใหม่ก่อน paid calls หรือจำกัด claim เป็น bounded multi-source case study. ห้ามเปลี่ยน precision target หลังดูผลเพื่อให้ผ่าน.

## 5. Gate ที่ต้องผ่านก่อนอ้างว่า concern ปิด

| Concern | หลักฐานที่ต้องได้ | ถ้าไม่ได้ |
|---|---|---|
| Real executable work | ทุก case มี frozen source/split, container verifier, ML full-DAG หรือ repo visible+regression+replay, auditor ผ่าน; รายงาน fail ด้วย | เรียก feasibility/partial ไม่ใช้แทน full pipeline |
| Decision locus | E1 matched no-fault parity และ controlled coordinator/shared-store faults ผ่าน; E2 แสดงผล operational จริง | จำกัดเป็น association ของ policy bundles ไม่อ้าง architecture-specific effect |
| Source diversity/uncertainty | ≥12 eligible projects, 6 corpora, 24 audited paired blocks และ project-level intervals/sensitivity | รายงาน bounded case study; ไม่อ้าง generalization/equivalence |
| Cost | Billing export reconcile ทุก attempt และ currency ระบุชัด | ตัด monetary real-LLM claim, รายงาน tokens/unknown cost |
| Advisor scope | READY belt, volunteer/stand-down, ≤3 models, Static+Central controls, RQ1 vector, RQ2/ablation แยก | แก้ protocol/manuscript ก่อนส่ง |

**Stop rule:** จบเมื่อรันทุก block ใน frozen cohort (หรือ eligibility ไม่ถึง 12 และบันทึกเหตุผล) และ audit ครบ; ไม่เพิ่มงานตาม sign ของผล. Provider unresolved/long-path failure เก็บ attempt marker, ไม่ยิงซ้ำใน ID เดิม; instrument amendment ต้องแยก version/ID และรายงาน prior exposure. ก่อนส่ง IEEE/AJSTR ต้องอัปเดต abstract, method, equations, results, figures, cost caveat และ limitations จาก audited outputs เท่านั้น. ผู้เขียน/ที่ปรึกษาต้องอนุมัติขอบเขตข้ออ้างและ target precision ก่อนระบุว่า “Major Revision closed”; ไม่มี design ใดรับประกันการตอบรับจากวารสาร.

**Storage gate:** raw runs เก็บใน D: short-path และขึ้น Git เฉพาะ code/locks/audit capsules ที่ไม่บรรจุ credential. ก่อน build project ใหม่เช็กพื้นที่ C: (Podman/WSL image store) และ D:; snapshot ขณะร่าง protocol เหลือราว 24 GB และ 205 GB ตามลำดับ. ถ้า C: <20 GB หรือ D: <100 GB ให้หยุด preflight/paid run และจัด storage plan แบบตรวจ exact target; ไม่ลบ image/container งานอื่นหรือ raw audit evidence อัตโนมัติ.
