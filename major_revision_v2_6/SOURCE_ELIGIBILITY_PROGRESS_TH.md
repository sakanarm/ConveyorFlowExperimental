# v2.6 — สถานะแหล่งข้อมูลก่อน Real-LLM main experiment

สถานะ ณ 12 ตุลาคม 2026: **ยังไม่ freeze main cohort และยังไม่เรียก LLM สำหรับ v2.6**. งานในไฟล์นี้คือ source eligibility เท่านั้น ไม่ใช่ผล RQ1/RQ2 หรือหลักฐานว่า CF-Fit ชนะ baseline.

## 1. ป้องกันการใช้เคสเดิมเป็นเคสใหม่

`build_prior_exposure_ledger_v1.py` ตรวจ `request_started.json` ในรากหลักฐาน v2.3–v2.5 ทั้ง workspace และ `D:\ConveyorFlowRuntime`. พบ 1,108 markers, ครอบคลุม 43 repository cases และ 4 ML corpora; marker นับเป็น prior exposure แม้การเรียก provider จะไม่สำเร็จ. ไม่มีรากที่กำหนดหายหรือ marker ที่จับคู่ case/corpus ไม่ได้. แหล่งข้อมูลคือ `prior_exposure_ledger_v1.json` ซึ่งเก็บเพียง relative path และ SHA-256 ของ marker ไม่เก็บ prompt, response หรือ API key. **จำนวน markers/API calls ไม่ใช่จำนวนตัวอย่างอิสระ**.

`build_unexposed_candidate_queue_v1.py` ตรึงลำดับ hash ของทุก project/case จาก BugsInPy manifest โดยข้าม 43 เคสที่เคยเรียก LLM. ทั้ง 17 project มีอย่างน้อย 2 *metadata candidates* ที่ยังไม่ exposed; คำว่า metadata candidate ไม่ได้หมายความว่ารัน test ใน container ได้. ดู `unexposed_candidate_queue_v1.json`.

## 3. ผลต่อแผนวิจัย

- 17 project ใน manifest ไม่เท่ากับ 17 project ที่ใช้ main ได้. ย่อหน้านี้บันทึก checkpoint ระยะแรกที่ตรวจ PySnooper และ Sanic; สถานะที่ใหม่กว่าของ Cookiecutter และ FastAPI อยู่ในส่วนต่อท้ายเอกสาร. หลัง FastAPI ผ่าน candidate gate แล้วก็ยังต้องคัด repository อิสระอื่นตามคิวที่ตรึงไว้.
- เป้าหมาย 12 distinct qualified projects ยัง **ไม่รับประกัน**. หากไม่ถึง ให้หยุดที่ eligibility outcome และจำกัดข้ออ้างเป็น bounded multi-source feasibility ตาม protocol; ห้ามเพิ่มเคสเพราะทิศทางผล CF-Fit ไม่ถูกใจ.
- ก่อนยิง MFEC main ต้องทำ gold-free repair candidate/public regression, ML corpora เพิ่มและ full-DAG smoke, ability/difficulty/analysis lock, model-version/cost gate, matched decision-locus test และ freeze paired cohort. จากนั้นจึงรัน CF-Fit เทียบ Central-Rule-Matched กับ Static-Owners บน READY belt เดียวกัน และรายงาน throughput/time/utilization/cost เป็น trade-off.

การตรวจซ้ำแบบไม่เรียก LLM: `python major_revision_v2_6/build_prior_exposure_ledger_v1.py --write`, `python major_revision_v2_6/build_unexposed_candidate_queue_v1.py --write`, `python major_revision_v2_6/preflight_sanic_v1c.py --audit`; ส่วน PySnooper audit ให้เรียก script เดียวกันใน WSL/Podman environment. ทุก script ปฏิเสธการเขียนทับ lock/ledger ที่เปลี่ยนไป.

Lock ของ v1b ที่เขียนจาก Windows ใช้ absolute host path จนตรวจบน WSL ไม่ผ่านก่อน build; เก็บ lock เดิมใน `lock_hostpath_failed.json` และแก้เป็น canonical `/mnt/d/...` ก่อนผล test. ไม่ตีความ v1/v1b เป็นผลบั๊กหรือผล policy.

v1c ผ่าน public contrast ตาม frozen order สองเคส: `fastapi_11` มี 6 public nodes, buggy fail 6/6, fixed pass 6/6; `fastapi_8` มี 1 node, buggy fail 1/1, fixed pass 1/1. ทั้งสอง record ระบุ `provider_calls=0`; ดู raw records และ JUnit XML ที่ `D:\ConveyorFlowRuntime\v2_6\fastapi_preflight_multinode_v1c`.

ด่าน candidate ของ FastAPI freeze ก่อนเรียก LLM: candidate image มีเฉพาะ buggy `fastapi/` package; fixed checkout และ public tests อยู่ฝั่ง verifier แยกจาก candidate. Public regression nodes ที่ไม่ใช่ visible bug ถูกเลือกด้วย hash rule คงที่ก่อนดู outcome, 3 nodes ต่อเคส; ต้องผ่านทั้ง buggy/fixed และห้ามเปลี่ยน node ที่เลือกเมื่อผลไม่ผ่าน. การ collect ชุด `tests/` ทั้งหมดล้มจาก imports ของ tutorial examples จึงมี amendment v1b ให้ collect เฉพาะ top-level `tests/test_*.py` ก่อนเลือก node. v1c/v1d แก้เฉพาะการ resume หลังไฟล์หลักฐานเคสแรกถูกสร้างแล้ว ไม่เปลี่ยน selection rule หรือเกณฑ์ผ่านหลังเห็นผล.

ผล: `fastapi_11` visible buggy fail 6/6 และ 3 public regressions ผ่านทั้ง buggy/fixed; `fastapi_8` visible buggy fail 1/1 และ 3 regressions ผ่านทั้งคู่. `audit_fastapi_two_candidate_gates_v1.py` ตรวจ ledger, hashes, JUnit XML, hash selection, source-map equality และ absence ของ fixed/protected roots ใน candidate ซ้ำอย่างอิสระ; capsule คือ `fastapi_two_candidate_gates_capsule_v1.json`, raw evidence อยู่ `D:\ConveyorFlowRuntime\v2_6\fastapi_candidates_v1`. สถานะคือ **FastAPI สองเคสผ่าน source eligibility เท่านั้น** (`provider_calls=0`), ไม่ใช่ผล Real-LLM และยังไม่ใช่หลักฐาน RQ1/RQ2. ยังไม่ freeze main cohort เพราะต้องมี repository อิสระอื่นและ ML corpora ที่ผ่าน gate ตาม protocol; ยังไม่อ้างว่า Major Revision ปิดแล้ว.

## 5. เริ่ม Scrapy ตาม frozen source order

หลัง FastAPI ผ่าน ได้สร้าง `freeze_scrapy_source_queue_v1.py` และตรึง `scrapy_source_queue_v1/queue.json` กับ `lock.json` สำหรับ 40 เคสที่ยังไม่เคยเรียก provider. เคสแรกตาม hash order คือ `scrapy_39`, `scrapy_34`; metadata ของ Scrapy ใช้ `python -m unittest -q` และบางเคสมีหลายคำสั่ง/หลาย test files จึงตรึง **ทุกคำสั่ง** ที่ประกาศไว้ก่อนเห็นผล ไม่เลือกเฉพาะ node ที่ผ่าน. ขั้นนี้ตรวจเพียง metadata และคำสั่งสาธารณะ (`provider_calls=0`): **ยังไม่ได้ build container, ยังไม่ผ่าน public contrast/candidate gate และยังไม่เริ่ม Real-LLM**. ขั้นต่อไปคือสร้าง environment profile ที่เปิดเผย deviation แล้วรัน buggy/fixed ตามคิวเดิม.
